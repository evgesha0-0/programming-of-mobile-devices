# Backend Smart Cat Feeder

Backend хранит централизованное состояние кормушек, расписания, очередь ручных команд и
историю кормлений. HTTP API реализован на Fastify, данные хранятся в PostgreSQL.

## Структура

- маршруты описывают HTTP-контракт и JSON Schema;
- сервисы реализуют бизнес-правила и преобразование ответов;
- репозитории содержат PostgreSQL-запросы и границы транзакций;
- миграции являются источником истины для структуры базы данных;
- единый обработчик формирует безопасные ответы об ошибках.

## Модель данных

### `devices`

Хранит зарегистрированные устройства, последнее принятое состояние и текущую
`schedule_revision`.

### `schedules`

Хранит расписания автоматического кормления. Изменения получают монотонно растущую ревизию.
Удаление мягкое: запись сохраняется с `deleted_at`, чтобы Khadas получил tombstone при
синхронизации, а история кормлений не потеряла ссылочную целостность.

### `feeding_commands`

Очередь ручных команд. `command_id` создаётся Android-клиентом и является ключом
идемпотентности. Команда содержит назначенный backend идентификатор `feeding_id`, срок
действия и монотонный статус выполнения.

### `feedings`

Единая история ручных и автоматических кормлений. Для ручной команды запись создаётся
одновременно с командой и затем дополняется фактическим результатом Khadas.

## Формат ошибок

Ошибки API имеют общий вид:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Описание ошибки",
    "request_id": "req-id"
  }
}
```

Используются коды `VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT`, `INTERNAL_ERROR` и
`SERVICE_UNAVAILABLE`. Внутренние сообщения PostgreSQL и секреты клиенту не передаются.

## Состояние сервиса

```http
GET /health
GET /ready
```

`/health` отражает доступность HTTP-приложения. `/ready` дополнительно проверяет соединение
с PostgreSQL.

## Состояние устройства

```http
GET /api/v1/devices/{device_id}/state
PUT /api/v1/devices/{device_id}/state
```

`PUT` принимает только состояния, которые может сообщить Khadas. Значение `offline`
зарезервировано для вычисления backend. Более старая метка `reported_at` отклоняется;
точный повтор состояния идемпотентен.

## Расписания Android

```http
GET    /api/v1/devices/{device_id}/schedules
POST   /api/v1/devices/{device_id}/schedules
PUT    /api/v1/devices/{device_id}/schedules/{schedule_id}
DELETE /api/v1/devices/{device_id}/schedules/{schedule_id}
```

Создание, изменение и мягкое удаление выполняются в транзакции вместе с увеличением
`devices.schedule_revision`. Время имеет формат `HH:mm:ss`, дни недели уникальны, timezone
проверяется как идентификатор IANA, масса соответствует `numeric(8,2)`.

## Синхронизация расписаний Khadas

```http
GET /api/v1/devices/{device_id}/sync/schedules?known_revision={revision}
```

Метод возвращает полный снимок, включая tombstone-записи. Ревизия, серверная метка времени
и расписания читаются одним SQL-запросом, поэтому ответ не смешивает разные состояния базы.

## Ручное кормление

```http
POST /api/v1/devices/{device_id}/feeding-commands
```

Новая команда и начальная запись `feedings` создаются в одной транзакции. Первый запрос
возвращает `202 Accepted`. Точный повтор с теми же `device_id`, `command_id`,
`portion_grams` и `expires_at` возвращает сохранённый ресурс с `200 OK`, включая повтор после
истечения срока команды. Другое содержимое под тем же `command_id` возвращает
`409 CONFLICT`.

Принятие команды означает только постановку в очередь. Успешная физическая выдача
подтверждается позднее результатом Khadas со статусом `completed`.

Khadas получает ожидающие команды через:

```http
GET /api/v1/devices/{device_id}/commands/pending?limit={limit}
```

`limit` по умолчанию равен `10` и должен быть положительным целым числом. Перед чтением
очереди backend в одной транзакции переводит просроченные команды и связанные записи
кормлений из `pending` в `expired`. Ответ содержит только непросроченные команды в порядке
`created_at`, `command_id` и серверную метку `server_time`.

Начало выполнения команды подтверждается методом:

```http
POST /api/v1/devices/{device_id}/commands/{command_id}/ack
```

Backend проверяет совпадение `feeding_id`, срок команды и её текущее состояние, затем в одной
транзакции переводит команду и кормление из `pending` в `running`. Точный повтор с тем же
`started_at` идемпотентен. Просроченная команда переводится в `expired`; несовпадающие
идентификаторы и недопустимые переходы возвращают `409 CONFLICT`.

Результат ручного кормления принимается методом:

```http
POST /api/v1/devices/{device_id}/feedings/{feeding_id}/result
```

Backend принимает итог `completed` или `failed` только для кормления в состоянии `running`.
Идентификаторы, порция и `started_at` должны совпадать с сохранённой командой. Команда и
кормление завершаются в одной транзакции. Для `completed` обязательна фактическая масса,
для `failed` — код и безопасное описание ошибки. Точный повтор результата идемпотентен,
другое содержимое под тем же `feeding_id` возвращает `409 CONFLICT`.

## События кормления по расписанию

```http
POST /api/v1/devices/{device_id}/feeding-events
```

Khadas передаёт завершённое или неуспешное автоматическое кормление вместе с `feeding_id`,
`schedule_id`, запланированной и фактической массой, временными метками и сведениями об ошибке.
Событие принимается и для мягко удалённого расписания, если устройство выполнило его до получения
tombstone. Первый запрос возвращает `201 Created`, точный повтор — сохранённое событие с `200 OK`,
а другое содержимое под тем же `feeding_id` — `409 CONFLICT`.

## История кормлений

```http
GET /api/v1/devices/{device_id}/feedings?limit=50&cursor={cursor}
```

Метод возвращает ручные и автоматические кормления от новых к старым. `limit` по умолчанию равен
`50`, допустимый диапазон — от `1` до `100`. `cursor` непрозрачен для клиента и передаётся без
изменений из `next_cursor` предыдущего ответа. Пустая следующая страница обозначается значением
`null`. Неизвестное устройство возвращает `404 NOT_FOUND`, некорректная пагинация —
`400 VALIDATION_ERROR`.

Полное состояние отдельного кормления доступно по идентификатору:

```http
GET /api/v1/devices/{device_id}/feedings/{feeding_id}
```

Ответ дополнительно содержит безопасное описание ошибки `error_message`. Поиск выполняется по паре
`device_id` и `feeding_id`, поэтому кормление другого устройства не возвращается. Неизвестная или
не принадлежащая устройству запись возвращает `404 NOT_FOUND`.

## Авторизация

Механизм пользовательских токенов Android и учётных данных Khadas пока не реализован.
Маршруты нельзя публиковать во внешней сети до проверки токена и принадлежности
`device_id` вызывающей стороне.
