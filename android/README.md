# Android — Smart Cat Feeder

Первый клиент на Java для управления кормушкой через существующий контракт REST API.

## Что сделано

- Настройка адреса backend, UUID устройства и пользовательского токена.
- Получение последнего известного состояния кормушки.
- Ручная выдача порции с подтверждением и проверкой результата.
- Автоматическая проверка ручной команды, пока приложение открыто.
- Уведомление о завершении, ошибке или истечении срока команды; результат сохраняется на экране.
- Создание, редактирование и удаление расписаний.
- История кормлений с загрузкой следующих страниц.
- Обработка недоступного сервера и основных HTTP-ошибок.

Android обращается только к backend, не управляет GPIO и не исполняет расписания самостоятельно.
Код backend, Linux-компонент и общий контракт этой работой не меняются.

## Сборка

Открыть каталог `android` в Android Studio. Требуются JDK 17, Android SDK Platform 35 и Build Tools 34.0.0.
Gradle 8.9 загружается через wrapper; Android Gradle Plugin — 8.7.3.

```powershell
.\gradlew.bat testDebugUnitTest lintDebug assembleDebug
```

APK: `app/build/outputs/apk/debug/app-debug.apk`.
Минимальная версия телефона — Android 8.0 (API 26).

## Подключение

На вкладке «Связь» указать адрес сервера без `/api/v1`, UUID кормушки и пользовательский токен.
Провайдер авторизации ещё не согласован командой, поэтому пока токен вводится вручную.
Адрес и UUID сохраняются локально. Токен остаётся в памяти процесса, не пишется в настройки,
не попадает в backup и не добавляется в репозиторий.

Для сервера на компьютере из стандартного Android Emulator использовать `http://10.0.2.2:3000`.
HTTP разрешён только в debug и только для `10.0.2.2`, `localhost`, `127.0.0.1`.
Release использует HTTPS. На реальном телефоне нужен доступный ему HTTPS-сервер.

В текущей ветке backend реализованы только `/health` и `/ready`.
До появления методов `/api/v1/devices/...` приложение будет показывать ошибку 404.
Приложение не подменяет отсутствующий API вымышленными данными.

## Ручная команда

Перед первой отправкой сохраняется тело запроса: UUID `command_id`, масса и `expires_at`.
При потере ответа нужно нажать «Повторить запрос»: отправляется то же тело,
поэтому по контракту backend повторная выдача не создаётся.
Команда сохраняется и при закрытии приложения; она привязана к адресу сервера и UUID кормушки.
После ответа сохраняется `feeding_id`, по которому кнопка «Проверить результат» запрашивает итог.
`pending` и `running` не показываются как успешная выдача.

После получения `feeding_id` приложение также проверяет результат автоматически раз в 5 секунд.
При сетевой ошибке пауза увеличивается до 10, 20, 40 и максимум 60 секунд.
Проверка отправляет только GET, не создаёт новую команду, прекращается после конечного результата
и при сворачивании приложения. При возвращении на экран она возобновляется.
Ответ, пришедший от остановленной проверки или от предыдущего подключения, игнорируется.
Для результата проверяются `feeding_id`, `command_id`, источник, статус, масса и время завершения.

Для системных уведомлений на Android 13+ нужно нажать «Включить уведомления» и разрешить их.
При отказе результат всё равно показывается и сохраняется на экране. Проверка выполняется
только пока приложение открыто: фоновые уведомления при закрытом приложении пока не реализованы.
Обработка результата атомарно удаляет ожидающую команду, поэтому повторный ответ не вызывает
ещё одно уведомление. Стабильный идентификатор уведомления дополнительно исключает дубликаты
одного кормления в системной шторке.

Пока срок действия принят за 5 минут; окончательный срок и аппаратные ограничения порции
требуют согласования с backend и Linux-командой. Проверяется положительная масса с точностью
до двух знаков и предел представления `numeric(8,2)`, а не безопасный размер физической порции.
После истечения срока команду можно убрать с экрана. Это не отмена на сервере:
перед следующей подачей нужно проверить историю.

## Проверка вручную

1. Сохранить неверный UUID или HTTP-адрес внешнего сервера — приложение должно отклонить ввод.
2. Получить состояние с тестового backend; проверить `online`, `offline`, `error`.
3. Отправить команду: `202/pending` должен отображаться как ожидание кормушки.
4. Потерять ответ после сохранения команды сервером, закрыть и открыть приложение, повторить запрос.
   В backend должна остаться одна команда с тем же `command_id`.
5. Проверить результат для `completed`, `failed` и `expired`, затем историю и пагинацию.
6. Создать, изменить и удалить расписание, обновляя список после операции.
7. Проверить ошибки 401, 403, 404, 409 и потерю сети.
8. Оставить приложение открытым после отправки команды: `pending` → `running` → `completed`
   должны обновиться без нажатия кнопки, а проверка — остановиться после результата.
9. Свернуть приложение во время проверки, затем открыть: после сворачивания не должно быть
   новых запросов опроса; результат старого незавершённого запроса не должен менять экран.
10. На Android 13+ разрешить и запретить уведомления. Проверить одно уведомление о результате
    при разрешении и сохранённый результат на экране при отказе.

Unit-тесты проверяют настройки подключения, порции, создание команды и настоящий HTTP-обмен
с локальным тестовым сервером, включая заголовок авторизации и запрет перенаправлений.
Дополнительные тесты проверяют валидацию результатов, паузы повторов, завершение опроса,
остановку при уходе с экрана и игнорирование устаревших ответов без ожидания реального времени.
Проверка физической выдачи и сквозные сценарии требуют готового backend и Khadas.
