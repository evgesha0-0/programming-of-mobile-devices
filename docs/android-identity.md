# Identity Android-пользователя

## Статус решения

Android уже передаёт значение из текущей сессии как `Authorization: Bearer <token>`, запрещает
управляющие символы в токене и не пересылает заголовок при redirect. Токен вводится вручную и
живёт только в памяти процесса; адрес backend и `device_id` сохраняются отдельно без токена.

Ручной ввод является временным режимом разработки. Для пользовательской авторизации выбран
OIDC-провайдер Keycloak. REST-клиент останется независимым от формата токена: после входа он
продолжит передавать полученный access token в том же заголовке.

## Провайдер и способ входа

- Провайдер identity: Keycloak с отдельным realm проекта.
- Realm: `smart-cat-feeder`; issuer задаётся backend через окружение для конкретного deployment.
- Android регистрируется как public OIDC client `smart-cat-feeder-android` без client secret.
- Audience backend API: `smart-cat-feeder-api`.
- Вход выполняется по Authorization Code Flow с PKCE `S256` через системный браузер.
- Встроенный WebView и Resource Owner Password Grant не используются.
- Пароль, MFA и восстановление учётной записи обрабатывает только Keycloak; Android и backend
  пароль пользователя не получают.
- После возврата по зарегистрированному redirect URI Android обменивает code на токены по
  защищённому каналу и создаёт пользовательскую сессию.
- Базовый пользовательский сценарий — самостоятельная регистрация по подтверждённому email и
  вход по email/паролю на странице Keycloak. MFA может быть включена политикой realm без изменения
  Android API-контракта.

Для release-сборки ручной ввод токена должен быть удалён. До реализации OIDC-входа он допустим
только как временный debug-сценарий.

## Формат и проверка access token

Access token — подписанный JWT, выпущенный Keycloak для audience backend API. Backend проверяет
подпись по OIDC Discovery/JWKS и принимает только явно разрешённый асимметричный алгоритм
`RS256`. Неподписанные токены, другой issuer, другая audience и симметричные алгоритмы не
принимаются.

Обязательные claims:

| Claim | Назначение |
|---|---|
| `iss` | точное совпадение с настроенным OIDC issuer |
| `sub` | стабильный идентификатор пользователя у провайдера |
| `aud` | должен содержать audience backend API |
| `exp` | срок окончания действия access token |
| `iat` | время выпуска токена |
| `jti` | уникальный идентификатор токена для аудита и точечного запрета |

`nbf`, если присутствует, также проверяется. Допустимое расхождение часов — не более 30 секунд.
`email`, `name` и `preferred_username` могут использоваться для отображения, но не определяют
identity и права доступа. Внутренний ключ внешнего пользователя образует пара `(iss, sub)`.

Срок жизни access token — 10 минут. Access token не передаётся в URL, тело запроса, логи или
аналитику и не используется как идентификатор записи в PostgreSQL.

## Обновление и отзыв

- Android получает refresh token вместе с access token и хранит его в защищённом хранилище,
  привязанном к Android Keystore.
- Refresh token ротируется при каждом обновлении. Повторное использование старого refresh token
  аннулирует соответствующую сессию.
- Максимальный период бездействия refresh-сессии — 30 дней, абсолютный срок — 90 дней.
- После `401` Android выполняет одну попытку обновления и один повтор исходного запроса. Циклические
  повторы запрещены. `403` не запускает обновление токена.
- Выход завершает сессию у провайдера, отзывает refresh token и удаляет локальные токены.
- Backend не принимает refresh token и не выпускает пользовательские токены самостоятельно.

Подписанный access token проверяется локально и после отзыва сессии может оставаться действительным
до окончания своих 10 минут. Удаление доступа пользователя к конкретной кормушке действует
немедленно, потому что membership проверяется в PostgreSQL на каждом запросе.

## Доступ пользователя к кормушке

Роль относится к конкретному `device_id` и поэтому не хранится в глобальном OIDC-токене. Backend
сопоставляет `(iss, sub)` с внутренним пользователем и отдельно проверяет membership устройства.
Знание UUID кормушки доступа не даёт.

Для первой версии фиксируются две роли:

| Действие | `owner` | `viewer` |
|---|:---:|:---:|
| Читать состояние кормушки | да | да |
| Читать расписания | да | да |
| Читать историю и детали кормлений | да | да |
| Создавать, изменять и удалять расписания | да | нет |
| Создавать команду ручного кормления | да | нет |
| Управлять доступом других пользователей | да | нет |

У устройства ровно один `owner` и может быть несколько `viewer`. Передача владения выполняется
атомарно; удалить последнего владельца без передачи владения нельзя. Device token Khadas не
создаёт пользовательский доступ и не может использоваться вместо Android access token.

Первичное назначение владельца в первой версии выполняет административная операция backend после
того, как пользователь хотя бы один раз вошёл через OIDC. Публичный claim/pairing устройства не
вводится без отдельного одноразового кода и отдельного контракта безопасности.

## Ответы backend

- `401 UNAUTHORIZED`: токен отсутствует, повреждён, просрочен, имеет неверную подпись, issuer или
  audience либо запрещён по `jti`.
- `403 FORBIDDEN`: токен действителен, но пользователь не связан с `device_id` или его роли
  недостаточно для операции.
- `404 NOT_FOUND`: ресурс не существует внутри устройства, к которому доступ уже подтверждён.

Backend получает пользовательскую identity только из проверенного токена. Идентификатор
пользователя из параметров или тела запроса не используется для авторизации.

## Следующий этап реализации

Для реализации потребуются валидация OIDC JWT и кеширование JWKS, таблицы внешних пользователей и
membership устройств, административное назначение первого владельца, middleware Android-маршрутов
и тесты матрицы прав `owner`/`viewer`.
