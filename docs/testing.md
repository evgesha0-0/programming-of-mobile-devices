# Интеграционное тестирование

Тестовый контур должен включать backend на TypeScript/NestJS с тестовой PostgreSQL, Android-клиент или его REST-тесты и Linux-приложение на TypeScript/Node.js либо его программный симулятор. Проверки выполняются по контракту [api.md](api.md).

## Сквозные сценарии

### 1. Android создаёт расписание — Khadas получает его

1. Android отправляет `POST /api/v1/devices/{device_id}/schedules`.
2. Backend сохраняет расписание и увеличивает `schedule_revision`.
3. Khadas запрашивает `/sync/schedules` и получает новое расписание.
4. Проверяется совпадение `schedule_id`, `time_local`, `days_of_week`, `timezone`, `portion_grams`, `active` и версии.

Ожидается: локальная копия заменена атомарно, повторная синхронизация не создаёт дубликатов.

### 2. Автоматическое кормление по расписанию

1. В симулированном времени наступает заданное локальное время и день недели.
2. Khadas самостоятельно начинает одно кормление без команды backend.
3. После выполнения создаёт событие `source=scheduled` с уникальным `feeding_id`.

Ожидается: механизм запущен один раз, backend не создавал ручную команду, событие содержит `schedule_id`.

### 3. Ручная команда Android — выполнение Khadas

1. Android отправляет команду с новым `command_id`.
2. Backend отвечает `202`, `status=pending` и возвращает `feeding_id`.
3. Khadas получает команду при опросе, подтверждает начало и выполняет её.
4. Android запрашивает состояние по `feeding_id`.

Ожидается: переходы `pending` → `running` → `completed` либо `failed`; принятие команды не показывается как успешная выдача.

### 4. Датчик фиксирует фактическую порцию

Симулятор датчика возвращает известное значение. Khadas отправляет его как `actual_grams`.

Ожидается: значение без изменения единиц сохранено в граммах и доступно через API. Для `completed` поле не равно `null`.

### 5. Результат появляется в истории Android

После получения результата Android запрашивает историю устройства.

Ожидается: кормление найдено по `feeding_id`, содержит правильные `source`, `portion_grams`, `actual_grams`, временные метки и итоговый `status`.

### 6. Khadas теряет связь

1. После успешной синхронизации отключается доступ к backend.
2. Наступает время локального расписания.
3. Khadas выполняет кормление и сохраняет событие локально.

Ожидается: расписание продолжает работать, событие не теряется, Android не получает ложного подтверждения до синхронизации.

### 7. Связь восстанавливается

После восстановления сети Khadas отправляет состояние, обновляет расписания и выгружает накопленные события.

Ожидается: события появляются в backend с исходными `feeding_id` и фактическими временами, а не со временем восстановления связи.

### 8. Повтор события не создаёт дубликат

Один и тот же запрос автономного события отправляется несколько раз с одинаковым `feeding_id`.

Ожидается: backend возвращает тот же ресурс, в истории существует одна запись. Конфликт содержимого под тем же идентификатором возвращает `409 CONFLICT`.

### 9. Ошибка двигателя или датчика

Симулятор поочерёдно создаёт `MOTOR_ERROR` и `WEIGHT_SENSOR_ERROR`.

Ожидается: кормление имеет `status=failed`, `finished_at` и соответствующий `error_code`; ошибка видна через состояние и историю, Android может сформировать уведомление.

### 10. Недоступный Khadas

Android создаёт ручную команду, пока Khadas не выполняет опрос.

Ожидается: состояние остаётся `pending`, затем после `expires_at` становится `expired`; UI не сообщает об успешной выдаче, а восстановившее связь устройство не выполняет просроченную команду.

## Дополнительные проверки контракта

- повтор `POST` ручной команды с тем же `command_id` и теми же данными возвращает тот же результат;
- тот же `command_id` с другим содержимым возвращает `409 CONFLICT`;
- невалидные день недели, IANA timezone, масса или временная метка возвращают единый `VALIDATION_ERROR`;
- устройство не может обращаться к данным другого `device_id`;
- Android без доступа к устройству получает `403 FORBIDDEN`;
- неизвестный ресурс возвращает `404 NOT_FOUND`;
- события передаются в UTC/ISO 8601, расписания сохраняют локальное время и timezone;
- изменение и удаление расписания увеличивают `schedule_revision`;
- после перезапуска Khadas не повторяет уже выполненную команду.

## Программная имитация оборудования

Linux-компонент следует разделить на TypeScript-логику выполнения и аппаратные адаптеры. Для разработки до подключения оборудования допускаются:

- программный адаптер GPIO, фиксирующий команды запуска и остановки механизма;
- программный датчик веса с настраиваемыми значениями, задержками и ошибками;
- управляемые часы для проверки расписаний без ожидания реального времени;
- имитация потери сети и устойчивая локальная очередь;
- сценарии нормальной выдачи, недовеса, перевеса, ошибки двигателя и ошибки датчика.

Симулятор должен использовать тот же TypeScript-интерфейс, что и будущий аппаратный адаптер. Если для реального оборудования потребуется драйвер на C или C++, он должен быть изолирован за этим интерфейсом. Конкретные GPIO-линии, драйверы и библиотеки нельзя фиксировать до выбора модели Khadas и оборудования.

## Критерий завершения интеграции

Все десять сценариев проходят без дубликатов и ложных успешных состояний; Android и Khadas используют зафиксированные методы, пути, поля и статусы; в журнале и тестовых данных отсутствуют секреты.
