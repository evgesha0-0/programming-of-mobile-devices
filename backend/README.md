# Backend Smart Cat Feeder

Backend системы Smart Cat Feeder на Fastify. Реализованы технические проверки HTTP-сервера и PostgreSQL, запуск SQL-миграций, начальная схема устройств, расписаний, ручных команд и истории кормлений, чтение и приём состояния устройства, CRUD и синхронизация расписаний. Остальные пользовательские методы API и авторизация ещё не реализованы.

## Технологии

- Node.js 24 LTS;
- TypeScript;
- Fastify;
- PostgreSQL;
- драйвер `pg`;
- `dotenv`;
- Docker Compose;
- встроенный тестовый раннер Node.js.

## Требования

- Node.js 24 LTS;
- npm;
- Docker и Docker Compose для локального PostgreSQL.

## Установка

Перейдите в каталог backend и установите зависимости:

```powershell
cd backend
npm install
```

## Настройка окружения

Создайте локальный `.env` на основе примера:

```powershell
Copy-Item .env.example .env
```

Демонстрационные значения согласованы с Docker Compose. Перед использованием вне локальной разработки замените пароль. Файл `.env` исключён из Git.

## PostgreSQL

Запустить PostgreSQL:

```powershell
docker compose up -d postgres
```

Проверить состояние контейнера:

```powershell
docker compose ps
```

Остановить контейнер:

```powershell
docker compose down
```

Данные PostgreSQL сохраняются в именованном Docker volume. Команда `docker compose down` его не удаляет.

## Миграции

После настройки `.env` и запуска PostgreSQL применить схему:

```powershell
npm run db:migrate
```

Команда берёт SQL из `migrations/`, фиксирует имя и SHA-256 файла в `schema_migrations`
и выполняет только ещё не применённые файлы. Повторный запуск сохраняет существующие данные.
Все ожидающие миграции одного запуска применяются в одной транзакции: ошибка откатывает весь
этот запуск вместе с записями журнала. Блокировка PostgreSQL сериализует параллельные запуски.
Ожидание блокировки ограничено 10 секундами, установка соединения — 5 секундами.

Файлы именуются `001_initial_schema.sql`, `002_описание_латиницей.sql` и так далее;
в имени допустимы только строчные латинские буквы, цифры и подчёркивания.
У каждого номера должен быть один файл. Применённые файлы не редактировать и не удалять:
для исправления схемы добавлять новую миграцию. Изменённая контрольная сумма или пропавшая
миграция останавливают запуск. Разница CRLF/LF между Windows и Linux не меняет сумму.
Не добавлять в SQL собственные `BEGIN`/`COMMIT`, они уже управляются инструментом запуска.

Миграции создают `devices`, `schedules`, `feeding_commands`, `feedings` и индексы очереди
и истории. Ограничения проверяют положительную массу, уникальные корректные дни недели,
связи кормлений с устройством, наличие фактической массы у завершённого кормления.
Триггер запрещает изменение идентификаторов и тела существующей ручной команды,
а также обратные переходы её статуса.

Для собранного приложения:

```powershell
npm run build
npm run db:migrate:production
npm start
```

При переносе сборки сохранять каталог `migrations/` рядом с `dist/` и `package.json`.
Миграции запускаются явно, сервер не меняет схему при старте. Автоматического удаления
таблиц или отката с потерей данных нет.

Дальнейшая бизнес-логика должна увеличивать `schedule_revision` и менять связанные строки
в одной транзакции, проверять IANA timezone и аппаратные границы порции, а также различать
точный повтор результата и конфликт. SQL-схема не заменяет эти проверки и авторизацию.

## Тесты

```powershell
npm test
```

Тесты HTTP-проверок используют подменённое подключение. Тесты схемы и миграций выполняют
настоящий PostgreSQL SQL в PGlite (PostgreSQL 18 в WebAssembly), устанавливаемом только
как dev-зависимость. Внешняя база и Docker для них не нужны. Проверяются повторный запуск,
контрольные суммы, полный откат ошибочной пачки, ограничения данных, переходы команды
и сохранение истории после мягкого удаления расписания.

Проверка типов включает исходники и тесты:

```powershell
npm run typecheck
```

Перед интеграцией также выполнить миграции на PostgreSQL 17 из Docker Compose и повторить
запуск с сохранёнными данными. PGlite не проверяет сетевое подключение драйвера `pg`
и конкуренцию нескольких отдельных серверных процессов.

## Технические endpoint

Проверка HTTP-сервера:

```http
GET /health
```

Успешный ответ:

```json
{
  "status": "ok",
  "service": "smart-cat-feeder-backend"
}
```

Проверка подключения к PostgreSQL:

```http
GET /ready
```

При доступной базе endpoint возвращает HTTP 200, при недоступной — HTTP 503. `/health` от состояния PostgreSQL не зависит.

## API состояния устройства

Реализованы методы зафиксированного контракта:

```http
GET /api/v1/devices/{device_id}/state
PUT /api/v1/devices/{device_id}/state
```

`GET` возвращает последнее известное состояние, ошибку и ревизию расписаний. `PUT` принимает
отчёт Khadas, запрещает значение `offline` и атомарно обновляет запись только для более новой
метки `reported_at`. Точный повтор с той же меткой и тем же содержимым идемпотентен;
устаревший или конфликтующий отчёт получает `409 CONFLICT`. Неизвестное устройство получает
`404 NOT_FOUND`, а невалидные UUID, временные метки, статусы и лишние JSON-поля —
`400 VALIDATION_ERROR`.

Маршруты пока не выполняют авторизацию: провайдер Android и механизм учётных данных Khadas
в контракте ещё требуют согласования. Это не следует использовать как публично доступный API
до реализации проверки токенов и принадлежности `device_id`.

## API расписаний

Реализованы Android-методы:

```http
GET    /api/v1/devices/{device_id}/schedules
POST   /api/v1/devices/{device_id}/schedules
PUT    /api/v1/devices/{device_id}/schedules/{schedule_id}
DELETE /api/v1/devices/{device_id}/schedules/{schedule_id}
```

Создание, полное изменение и мягкое удаление расписания атомарно увеличивают
`devices.schedule_revision` и записывают ту же ревизию в `schedules.revision`. Удалённые
расписания не возвращаются Android, но сохраняются в базе для будущей синхронизации Khadas
и целостности истории кормлений. Транзакция откатывает увеличение ревизии при любой ошибке.

Входные данные проверяются до SQL: время принимает формат `HH:mm:ss`, дни недели должны быть
непустыми и уникальными, timezone проверяется через базу IANA среды Node.js, а масса должна
помещаться в `numeric(8,2)` без неявного округления. Неизвестные или уже удалённые расписания
возвращают `404 NOT_FOUND`.

Для Khadas реализована синхронизация полным снимком:

```http
GET /api/v1/devices/{device_id}/sync/schedules?known_revision={revision}
```

Ответ содержит текущую `schedule_revision`, серверную метку `generated_at`, активные
расписания и tombstone-записи с `deleted_at`. Снимок и ревизия читаются одним SQL-запросом,
поэтому параллельное изменение расписания не может дать смешанное состояние. Даже при
совпадении `known_revision` возвращается полный снимок согласно текущему контракту.
